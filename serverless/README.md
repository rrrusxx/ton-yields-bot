# TON Yields Bot on Telegram Serverless (prototype)

The interactive part of TON Yields Bot, run by Telegram itself on [Telegram Serverless](https://core.telegram.org/bots/serverless): no server of our own. The daily post stays on GitHub Actions (Serverless has no scheduler). This folder is a prototype for the **test bot only** (@ton_yields_test_bot and @ton_yields_test).

## What it does

- **/yields widget.** `/start` or `/yields` in a private chat with the bot answers with a [widget](https://core.telegram.org/bots/widgets): a small live block inside the message with three tabs, TOP-5, GRAM and Stables. The TOP-5 comes with the widget (its shared state). The tabs ask the bot when tapped (`widget_query`). When the widget comes on screen again it asks for a fresh TOP-5 in the background, so an old widget in the chat shows the latest data once the bot has it.
- **Per-user answers under channel posts.** A button with callback data `only:TON` or `only:STABLE` under a channel post answers the person who tapped with that section, as an ephemeral reply (Bot API 10.4) that nobody else in the channel sees.

Data: `sample/snapshot.json`, the snapshot of the post of 2026-11-27 (the same rows the post showed, from `src/services/post_snapshot.ts` in the main bot). A live feed from the daily run is the next step (see Production).

## Layout

| Path | What it is |
|---|---|
| `tgcloud/handlers/message.js` | `/start` and `/yields`: sends the widget |
| `tgcloud/handlers/widget_query.js` | the widget's requests: `s:top`, `s:TON`, `s:STABLE` |
| `tgcloud/handlers/callback_query.js` | channel buttons `only:TON`, `only:STABLE`: ephemeral reply |
| `tgcloud/lib/yields.js` | pure helpers: compact rows, 1,024-byte packing, texts |
| `tgcloud/lib/widget_html.js`, `tgcloud/lib/data.js` | generated by `scripts/build.ts`: do not edit |
| `tgcloud/schema.js` | no tables yet |
| `widget/yields.html` | the widget's source (HTML, CSS, JavaScript in one file) |
| `sample/snapshot.json` | the sample data |
| `tests/yields_test.ts` | Deno tests, run by `deno task test` in the repository root |

Only `.js` files inside `tgcloud/` are deployed. After editing `widget/yields.html` or `sample/snapshot.json`, run `npm run build` (Deno), which also refuses a widget over Telegram's size limit.

## Setup (once, by the owner)

Serverless is a beta with a waitlist: until BotFather grants access, its Serverless screen says "You're on the waitlist" (both bots asked on 2026-11-27).

1. In @BotFather: your test bot → **Serverless** → turn it on. This lets Telegram manage the bot's webhook from now on.
2. In the same menu: **CLI Access** → **Access token**. It is a separate token from the bot's API token and looks like `app<id>:<secret>`. Never paste it into a chat, a file in the repository or a screenshot.
3. In Terminal, from the repository root, install the CLI into this folder and log in (paste the token when asked; it is saved in `.tgcloud/`, which git ignores):

```bash
cd serverless && npm install && npx tgcloud init && npx tgcloud login
```

`init` only adds what is missing (its docs and state folder) and never overwrites files here.

## Deploy and check

```bash
npm run deploy
```

```bash
npx tgcloud webhook sync --drop-pending
```

`--drop-pending` throws away updates that queued before Serverless was on, so the bot does not answer old messages. Then send `/yields` to the test bot.

`npx tgcloud status` shows what is not deployed yet, and `npx tgcloud run handlers/widget_query '{ id: "1", data: "s:TON" }'` runs a handler on the platform with local code (that one call fails at `answerWidgetQuery`, because the query id is not real, which is expected).

## Limits that shape the design

- **Widgets:** in production only in a private chat with the bot (groups, inline mode and forwards work on Telegram's test server only). At most 32 KB of HTML and 4 KB after zlib (ours: about 2.9 KB and 1.4 KB). No network inside the widget: it gets data only from the bot, as its state (up to 1,024 bytes) or as answers to its requests (up to 1,024 bytes, within 15 seconds). At most 5 requests per 5 seconds per user. Nothing scrolls inside a widget and its height stops at 600 px, so a tab shows at most 12 rows and counts the rest.
- **Ephemeral replies:** within 15 seconds of the tap, shown only to that person, delivery not guaranteed; the callback query is always answered.
- **Serverless:** plain JavaScript modules, no npm packages, SQLite and `fetch` (responses up to 30 MB). The platform owns the bot's webhook, so nothing else may poll this bot with `getUpdates` (the daily post only sends, which is fine). No scheduler. Price and quotas are not published on the official page; secondary sources say it is free during the launch period.

## Production (not done yet)

1. **Data feed.** The daily run publishes the post snapshot as JSON at a public address (GitHub Pages, planned for the "GRAM (TON) yields today" page anyway), and the handlers read it with `fetch`, cached in a table for about an hour. The alternative, a `tgcloud push` from the daily run with a `TGCLOUD_TOKEN` secret, deploys code every day and is not recommended.
2. **Serverless on @ton_yields_bot**, the same code, after the test bot has run for a while.
3. **Buttons under the daily post** ("💎 GRAM only", "💵 Stables only", callback data `only:TON` / `only:STABLE`) in `src/bot.ts`, only once the production handler is live: without it a tap just spins.
4. **The bot's profile:** a `/yields` command and a description that mention the widget.

## Not in this prototype

Inline mode with widgets, widgets in groups and forwards (test server only for now), the TON wallet in widgets, a Mini App.
